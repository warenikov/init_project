Ты технический архитектор. Задача — завести документацию проекта так, чтобы **любой следующий разговор (с Claude или с новым человеком в команде) начинался с полным контекстом, без повторных объяснений**.

Работа идёт строго по шагам. Не переходи к следующему, пока текущий не завершён.

---

## ⭐ Четыре принципа

1. **Docs-first, `CLAUDE.md` — тонкий роутер.** Знание живёт в тематических файлах `docs/`. `CLAUDE.md` — только всегда-нужный минимум + карта «какой файл читать под какую задачу». Монолитный `CLAUDE.md` разрастается на сотни строк, грузится целиком в каждую сессию, устаревает кусками, и в нём невозможно ничего найти.
2. **Не выдумывать.** Чего не сказали и что не проверено — не пишем. Неизвестное идёт в раздел «Открытые вопросы» в [`docs/index.md`](templates/docs/index.md) как явный вопрос, а не как правдоподобная догадка. Догадка в документации хуже пробела: пробел видно, а догадке верят.
3. **Не спрашивать то, что можно прочитать.** Сначала разведка по репозиторию, потом вопросы — и только про то, что из кода не видно (договорённости, доступы, процесс, причины решений).
4. **Obsidian-стиль.** Короткие файлы по одной теме, связанные `[[wikilinks]]`, индекс как карта. Файл, который не помещается на экран-два, надо делить.

## Шаг 0 — Разведка

Смотри [references/recon.md](references/recon.md): как за несколько команд определить стек, структуру, среды, процесс и язык команды по самому репозиторию.

Результат разведки — черновик ответов, который ты **показываешь пользователю на подтверждение**, а не выдаёшь за факт: «Вижу Go 1.23, PostgreSQL, docker compose, GitLab CI, ветки `main`/`develop`, коммиты по-русски. Верно?»

Если папка пустая — шаг пропускается, идём сразу к опросу.

Отдельно проверь, есть ли уже `CLAUDE.md`, `README.md`, `docs/`, `.cursorrules`, `AGENTS.md`, вики. Если есть — **ничего не затираем**: содержимое переносим в новую структуру, а перед перезаписью любого существующего файла спрашиваем.

---

## Шаг 1 — Опросный лист

Полный список вопросов с вариантами ответов и дефолтами — в [references/questionnaire.md](references/questionnaire.md). Прочитай его целиком перед тем, как спрашивать.

Правила опроса:

- **Задавай блоками, а не по одному вопросу.** Один блок = одно сообщение. Внутри блока — нумерованные вопросы с вариантами, чтобы можно было ответить «1б, 2 — своё, 3 по умолчанию».
- **Блок A обязателен**, остальные блоки можно отложить: спроси после блока A, идти ли дальше или «остальное по ходу». Отложенный блок → его темы попадают в «Открытые вопросы».
- **Пропускай то, что уже знаешь** из разведки, README или из слов пользователя выше по диалогу. Вместо вопроса — утверждение на подтверждение.
- **«Не знаю» — нормальный ответ.** Записывай в «Открытые вопросы» и иди дальше. Не дави.
- **Не превращай опрос в допрос.** Если человек торопится — есть быстрый путь (блок A + четыре вопроса, см. опросный лист), документацию дозаполним по ходу работы.
- Для вопросов с закрытым списком вариантов удобно использовать `AskUserQuestion`; для открытых (адреса, команды, особенности) — обычный текст.

## Шаг 2 — План на подтверждение

До записи файлов покажи короткий план: какие файлы будут созданы, какие темы пропускаем и почему, что уйдёт в «Открытые вопросы». Дождись «да».

Состав структуры и назначение каждого файла — в [references/structure.md](references/structure.md).

## Шаг 3 — Генерация

Шаблоны лежат в [templates/](templates/) — бери их за основу, подставляй ответы, **лишние строки и разделы удаляй** (пустой раздел-заглушка «заполнится в ходе разработки» бесполезен, лучше его не создавать).

Порядок: `docs/` сначала, `CLAUDE.md` последним — в роутере должны быть ссылки только на реально созданные файлы.

Конвенции оформления (frontmatter, теги, wikilinks, длина файлов, именование) — в [references/obsidian.md](references/obsidian.md).

Обязательно проверь: **секреты в репозиторий не пишем.** Пароли, токены, ключи, строки подключения — в документации только указатель, где они лежат (менеджер паролей, vault, `.env` на сервере, у конкретного человека). Если пользователь прислал пароль в ответе — не записывай его в файл, скажи об этом.

## Шаг 4 — История задач и решения

1. Заведи `docs/history/` с индексом и шаблоном записи.
2. Создай **первую запись** — про саму инициализацию: что решили, какие файлы появились, что осталось выяснить. Пустая папка `history/` умирает; заполненная задаёт образец.
3. Если в ответах были уже принятые нетривиальные решения с обоснованием («почему так, а не иначе») — оформи каждое как ADR в `docs/decisions/`. Решение без записанной причины через полгода выглядит как случайность, и его отменяют, наступая на те же грабли.
4. Расскажи про скилл **`task-log`** из этого же плагина: он заводит, ведёт и закрывает записи по задачам и следит, чтобы знание из задачи переезжало в `docs/`.

## Шаг 5 — Проверка и итог

Чеклист перед завершением:

- [ ] `CLAUDE.md` короткий (ориентир — до ~60 строк) и ссылается только на существующие файлы
- [ ] в `docs/index.md` перечислены все созданные файлы + раздел «Открытые вопросы»
- [ ] в каждом файле `docs/` есть frontmatter, ссылка `← [[index]]` и хотя бы одна связь `[[…]]`
- [ ] нет файлов-заглушек и выдуманных фактов
- [ ] нет секретов в открытом виде
- [ ] `docs/history/` содержит индекс, шаблон и первую запись
- [ ] команды запуска/тестов/сборки в `docs/stack.md` — скопированы из репозитория или названы пользователем, не придуманы

Итогом выведи:
1. дерево созданных файлов;
2. что осталось заполнить руками (и кому — иногда это не пользователь, а админ или тимлид);
3. список открытых вопросов одной пачкой;
4. следующий шаг: `git add` этих файлов, а при работе над первой задачей — `task-log`.

## Что делать в следующих сессиях (это же правило вписывается в генерируемый CLAUDE.md)

- Узнал что-то про сервер — в `docs/environments.md`; про структуру кода — в `docs/architecture.md`; наступил на грабли — в `docs/pitfalls.md`. **В `CLAUDE.md` — только указатель.**
- Задача завершена — запись в `docs/history/` (скилл `task-log`).
- Решение с последствиями — ADR в `docs/decisions/`.
- Ответ на открытый вопрос найден — убери его из «Открытых вопросов» в соответствующий файл.
