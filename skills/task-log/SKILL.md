Ты ведёшь журнал задач проекта. Журнал нужен не для отчётности, а чтобы через полгода можно было понять, **почему код такой** и **что уже пробовали**.

Записи лежат в `docs/history/`, индекс — `docs/history/index.md`, шаблон — `docs/history/template.md`. Конвенции проекта (префикс тикетов, имена веток, Definition of Done) — в `docs/workflow.md`; прочитай его перед работой.

Если `docs/history/` нет — предложи сначала запустить скилл `init-project`. Если пользователь не хочет полной инициализации, создай минимум: `docs/history/index.md` и `template.md` по образцу из `init-project`.

---

## Режимы

### `start` — завести запись

1. Определи идентификатор: номер тикета из трекера (`INF-12345`) или, если трекера нет, короткий slug.
2. Имя файла: `docs/history/YYYY-MM-DD-<тикет>-<короткий-slug>.md`. Slug — латиницей, kebab-case.
3. Заполни из шаблона: постановку — **словами заказчика**, не своим пересказом; ветку — по конвенции из `docs/workflow.md` (имя предложи, ветку сам не создавай, если не просили).
4. Добавь строку в раздел «В работе» индекса.
5. Проверь `docs/pitfalls.md` и прошлые записи по похожим словам — если по этой области уже обжигались, скажи об этом **до** начала работы. В этом вся окупаемость журнала.

### `update` — дописать ход

Дописывай в раздел «Что выяснили» по ходу работы, особенно:
- тупиковые ветки и почему не сработало — иначе следующий пойдёт туда же;
- неожиданное поведение системы;
- решения, принятые по дороге, и их причины.

Не переписывай уже написанное — добавляй. Журнал ценен хронологией.

### `done` — закрыть

1. Заполни «Что сделали», «Затронутые файлы», «Как проверить». **«Работает» без способа проверки — не результат.**
2. Frontmatter: `status: done`, `finished: YYYY-MM-DD`.
3. Перенеси строку из «В работе» в «Завершённые» с итогом в одну строку.
4. **Сбор знания — обязательный пункт.** Пройди по задаче и спроси себя:
   - Наступили на грабли → строка в `docs/pitfalls.md` (симптом → причина → что делать).
   - Приняли решение с альтернативами → ADR в `docs/decisions/`.
   - Узнали новое про среду, деплой, доступы → `docs/environments.md`.
   - Изменилась структура кода или появился новый компонент → `docs/architecture.md`.
   - Ответили на вопрос из «Открытых вопросов» `docs/index.md` → перенеси ответ в нужный файл и убери вопрос.
   Запиши в разделе «Куда переехало знание», что именно перенесено. Если ничего — так и напиши, это честный ответ.
5. Сверься с Definition of Done из `docs/workflow.md` и назови невыполненные пункты. Не объявляй задачу закрытой за пользователя, если что-то из DoD не сделано.

### `find` — найти прошлое

Поиск по журналу перед началом похожей работы:

```bash
grep -ril "<ключевое слово>" docs/history/ docs/pitfalls.md
```

Покажи, что нашлось, коротким пересказом: тикет, что делали, чем кончилось.

## Правила

- Одна задача — один файл. Файл на день или на релиз — только если так записано в `docs/workflow.md`.
- Пишем по факту, а не по плану: «сделали X» пишется после того, как сделали.
- Секреты и персональные данные в журнал не попадают — ни пароля, ни токена, ни дампа с реальными клиентами.
- Неудачная задача тоже документируется. Запись «пробовали X, не вышло, потому что Y» — самая полезная в журнале.
- Язык журнала — язык документации проекта.
