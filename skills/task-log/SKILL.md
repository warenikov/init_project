Ты ведёшь журнал задач проекта. Журнал нужен не для отчётности, а чтобы через полгода можно было понять, **почему код такой** и **что уже пробовали**.

---

## Шаг 0 — Разберись, какая структура уже есть (всегда, до любого действия)

Журнал мог завести другой скилл, другой человек или другой агент. **Подстраивайся под то, что есть, а не навязывай своё.** Переименовывать существующие файлы и менять устоявшуюся разметку нельзя — это ломает ссылки и злит команду.

```bash
ls docs/history/ docs/История/ docs/journal/ 2>/dev/null
ls docs/*.md 2>/dev/null
```

Что нужно установить:

| Что выясняем | Где смотреть | Если не нашлось |
|---|---|---|
| Папка журнала | `docs/history/`, иначе поиск по `docs/` на index + записи | `docs/history/` |
| Шаблон записи | `template.md` в папке журнала | шаблон ниже |
| **Именование файлов** | по существующим записям: `INF-12345.md`, `2026-09-20-INF-12345-slug.md`, `MM_DD_YYYY_name.md` | `YYYY-MM-DD-<тикет>-<slug>.md` |
| Разделы записи | заголовки в существующих записях и в шаблоне | шаблон ниже |
| Индекс и его разделы | `index.md` журнала: «В работе» / «Завершённые» или свои | создать |
| Правила процесса, DoD, ветки | `docs/workflow.md`, `docs/git-flow.md`, `docs/dev-rules.md`, `CLAUDE.md` | спросить у пользователя |
| Префикс тикетов | имена существующих записей, имена веток `git branch -a` | спросить |

**Правило:** структура проекта главнее этого скилла. Свои умолчания применяй только там, где в проекте ничего нет. Если записи называются `INF-12345.md` — следующая тоже `INF-12346.md`, а не по твоему формату.

Если журнала нет совсем — предложи запустить скилл `init-project`. Не хочет полной инициализации — создай минимум: `docs/history/index.md` (разделы «В работе» и «Завершённые») и `template.md`.

Если разделов «В работе» / «Завершённые» в индексе нет, а записи есть — спроси, добавить ли их, прежде чем менять структуру индекса.

## Режимы

### `start` — завести запись

1. Идентификатор: номер тикета из трекера или, если трекера нет, короткий slug.
2. Имя файла — **по конвенции проекта из шага 0**.
3. Заполни разделы существующего шаблона. Постановку пиши **словами заказчика**, не своим пересказом. Ветку — по конвенции из файла с правилами процесса; имя предложи, саму ветку не создавай, если не просили.
4. Добавь строку в раздел «В работе» индекса.
5. **Проверь прошлый опыт до начала работы:**
   ```bash
   grep -ril "<ключевое слово>" docs/history/ docs/pitfalls.md docs/ 2>/dev/null
   ```
   Если по этой области уже обжигались — скажи об этом сразу, до того как человек начнёт работать. В этом вся окупаемость журнала.

### `update` — дописать ход

Дописывай по ходу работы, особенно:
- тупиковые ветки и почему не сработало — иначе следующий пойдёт туда же;
- неожиданное поведение системы;
- решения, принятые по дороге, и их причины.

Не переписывай уже написанное — добавляй. Журнал ценен хронологией.

### `done` — закрыть

1. Заполни, что сделали, какие файлы затронуты и **как проверить результат**. «Работает» без способа проверки — не результат. Если в шаблоне проекта таких разделов нет — добавь их в эту запись, это улучшение, а не ломка структуры.
2. Во frontmatter: `status: done` и дата завершения. Если frontmatter в проекте не используется — помечай статус так, как принято в существующих записях.
3. Перенеси строку из «В работе» в «Завершённые» с итогом в одну строку.
4. **Сбор знания — обязательный пункт, не пропускать.** Пройди по задаче и разложи добытое по местам:
   - наступили на грабли → `docs/pitfalls.md` (симптом → причина → что делать); нет такого файла — заведи;
   - приняли решение с альтернативами → ADR в `docs/decisions/`;
   - узнали новое про среду, деплой, доступы → `docs/environments.md` или `docs/servers.md` — что есть в проекте;
   - изменилась структура кода, появился компонент → `docs/architecture.md`;
   - ответили на вопрос из «Открытых вопросов» → перенеси ответ в нужный файл, вопрос убери.

   Запиши в записи задачи, что именно перенесено. «Никуда» — честный ответ, но только после того, как проверил все пять пунктов.
5. Сверься с Definition of Done проекта и назови невыполненные пункты. **Не объявляй задачу закрытой за пользователя**, если что-то из DoD не сделано.

### `find` — найти прошлое

```bash
grep -ril "<ключевое слово>" docs/history/ docs/pitfalls.md
```

Покажи находки коротким пересказом: тикет, что делали, чем кончилось.

## Шаблон записи (если в проекте своего нет)

```markdown
---
tags: [task]
ticket: {{ТИКЕТ}}
status: in-progress
branch: {{ВЕТКА}}
started: {{ДАТА}}
finished:
---

# {{ТИКЕТ}} — {{Название}}

← [[index]]

## Постановка
## Что выяснили
## Что сделали
## Затронутые файлы
## Как проверить
## Осталось
## Куда переехало знание
```

---

## Правила

- Одна задача — один файл, если в проекте не принято иначе.
- Пишем по факту, а не по плану: «сделали X» — после того, как сделали.
- Секреты и персональные данные в журнал не попадают: ни пароля, ни токена, ни дампа с реальными клиентами.
- Неудачная задача документируется тоже. «Пробовали X, не вышло, потому что Y» — самая полезная запись в журнале.
- Язык журнала — язык остальной документации проекта.
